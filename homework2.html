Homework 2 · Wallet Cryptography

From Wallet Seed to Ethereum Address

Exploring the complete cryptographic pipeline: hashing, key derivation, and the cryptographic primitives that transform a human-readable mnemonic phrase into a secure Ethereum address.

Summary

An Ethereum wallet uses a layered cryptographic pipeline where each component serves a distinct purpose. The process begins with BIP-39, which converts a random mnemonic phrase into a deterministic seed. BIP-32 and BIP-44 then derive hierarchical keys from that seed, enabling a single backup phrase to generate unlimited accounts. The private key is transformed into a public key using secp256k1 elliptic-curve cryptography, which is then hashed with Keccak-256 to produce an Ethereum address. Finally, EIP-55 adds a checksum via mixed-case encoding to detect typos.

Each primitive addresses a different requirement: key management and derivation (BIP standards), one-way public-key relationships (secp256k1), irreversible fingerprinting (Keccak-256), and error detection (EIP-55). Together, they form a pipeline that balances security, usability, and compatibility with the broader cryptocurrency ecosystem.

Cryptographic Primitives

BIP-39: Mnemonic Sentence and Seed Generation

Purpose: Convert random entropy into human-readable backup phrases and derive a deterministic seed.

How it works:

  • Generate 128–256 bits of entropy (randomness)
  • Add a checksum (SHA-256 of entropy, first few bits)
  • Split into 11-bit chunks and map to words from a 2048-word dictionary
  • Result: 12–24 word mnemonic phrase (e.g., "abandon abandon abandon ... art")
  • Use PBKDF2-HMAC-SHA512 with 2048 iterations to derive a 512-bit seed from mnemonic + optional passphrase

Statistical properties: The mnemonic is deterministic given the entropy, but the entropy itself must be cryptographically random. The 2048 iterations of PBKDF2 slow down brute-force attacks. The passphrase acts as a second factor.

BIP-32: Hierarchical Deterministic (HD) Key Derivation

Purpose: Derive an unlimited number of private/public key pairs from a single seed in a tree structure.

How it works:

  • Use the 512-bit seed to generate a master private key and chain code
  • Derive child keys using HMAC-SHA512(chain_code, parent_key || index)
  • Split the 512-bit output: left 256 bits → child private key modifier, right 256 bits → new chain code
  • Support both hardened (private derivation) and non-hardened (public derivation) paths

Statistical properties: Each child key appears independent and uniformly random. The chain code ensures that knowing one child key does not reveal siblings. Hardened derivation prevents deriving child private keys from the parent public key.

BIP-44: Standard Derivation Paths

Purpose: Define a standard structure for HD wallets to organize accounts and addresses across multiple coins.

Path format: m / 44' / coin_type' / account' / change / address_index

  • 44' – BIP-44 standard (hardened)
  • coin_type' – Cryptocurrency (60' for Ethereum, hardened)
  • account' – Account number (0', 1', 2', ... hardened)
  • change – 0 for receiving, 1 for change (not hardened)
  • address_index – Address index (0, 1, 2, ... not hardened)

Example: m/44'/60'/0'/0/0 is the first Ethereum address of the first account.

Statistical properties: The standard path ensures wallets from different vendors can restore the same addresses. Hardened levels prevent key leakage attacks.

secp256k1: Elliptic-Curve Public-Key Cryptography

Purpose: Generate a public key from a private key in a one-way, computationally infeasible-to-reverse manner. Also used for digital signatures.

How it works:

  • Curve equation: y² = x³ + 7 (over a large finite field, ~2²⁵⁶)
  • Public key Q = k · G, where k is the private key and G is the generator point
  • The discrete logarithm problem (finding k from Q) is computationally infeasible
  • Used in Bitcoin and Ethereum for key generation and ECDSA signatures

Statistical properties: Public keys are uniformly distributed on the curve. The mapping is deterministic and one-way. Unlike RSA, secp256k1 provides the same security with much smaller keys (256 bits vs 2048+ bits).

Keccak-256: Hash Function

Purpose: Irreversibly hash the public key to derive an Ethereum address. Also used throughout Ethereum for transaction hashing, Merkle trees, and storage.

How it works:

  • Keccak is a sponge construction with permutation function
  • Ethereum uses Keccak-256 (256-bit output), which is not the same as SHA3-256 (different padding)
  • Input: 64-byte uncompressed public key (without 0x04 prefix)
  • Output: 32-byte hash, take last 20 bytes as Ethereum address

Statistical properties: Output is uniformly distributed, collision-resistant, and preimage-resistant. Even a 1-bit change in input produces a completely different hash (avalanche effect). The 160-bit address space (2¹⁶⁰ ≈ 10⁴⁸) makes collisions astronomically unlikely.

EIP-55: Mixed-Case Checksum Encoding

Purpose: Add error detection to Ethereum addresses without changing the underlying format or requiring extra characters.

How it works:

  • Take the lowercase hex address (without 0x)
  • Compute Keccak-256 hash of the lowercase address
  • For each hex character: if the corresponding hash digit ≥ 8, capitalize it; otherwise, keep lowercase
  • Result: mixed-case address like 0xAbCdEf...

Example: 0x5aAeb6053f3E94C9b9A09f33669435E7Ef1BeAed

Statistical properties: The checksum is deterministic and verifiable. A typo will almost always produce an invalid checksum (high error detection rate). It's backwards-compatible: old software ignores case, new software validates it.

Key Distinctions

Key Generation vs Key Derivation

  • Key Generation: Creating a new cryptographic key from random entropy (e.g., BIP-39 mnemonic generation, secp256k1 scalar multiplication)
  • Key Derivation: Deterministically computing new keys from existing key material (e.g., BIP-32/BIP-44 child key derivation, PBKDF2 seed expansion)

Public-Key Cryptography vs Hashing

  • Public-Key Cryptography (secp256k1): Mathematical trapdoor function. Easy to compute public key from private key, infeasible to reverse. Supports signatures and key agreement. Has algebraic structure (point addition).
  • Hashing (Keccak-256): One-way compression function. Fixed-size output regardless of input size. No algebraic structure. Used for fingerprinting, commitments, and addresses. No way to reverse or derive related outputs.

Checksums vs Encoding

  • Checksums (EIP-55): Error-detection mechanism. Adds redundancy to detect (not correct) errors. In EIP-55, achieved via mixed-case encoding.
  • Encoding: Representation format for data. Examples: hexadecimal (base-16), base58 (Bitcoin addresses), base64. Encoding is reversible and doesn't add security, just readability.

Historical and Temporal Context

1977
RSA – First practical public-key cryptosystem (Rivest, Shamir, Adleman). Based on integer factorization hardness.
2001
SHA-2 / SHA-512 – NIST standardized the SHA-2 family (SHA-224, SHA-256, SHA-384, SHA-512). Based on Merkle–Damgård construction.
2012
BIP-32 – Hierarchical Deterministic Wallets introduced by Pieter Wuille. Enabled deriving unlimited keys from a single seed.
2013
BIP-39 – Mnemonic code for generating deterministic wallets. Introduced human-readable 12-24 word backup phrases.
2014
BIP-44 – Multi-account hierarchy for deterministic wallets. Standardized derivation paths across cryptocurrencies.
2015
SHA-3 – NIST standardized SHA-3 based on Keccak sponge construction. Different internal design from SHA-2. Ethereum uses Keccak-256 (pre-standardization variant).
2016
EIP-55 – Mixed-case checksum addresses for Ethereum. Added error detection without breaking existing addresses.

SHA-2 / SHA-512 vs Keccak / SHA-3

SHA-2 family (including SHA-512) uses the Merkle–Damgård construction: input is padded and processed in blocks through a compression function, with each block's output chained to the next. Vulnerable to length-extension attacks.

Keccak / SHA-3 uses a sponge construction: input is absorbed into a state array, then permuted repeatedly. Output is squeezed from the state. Resistant to length-extension attacks and structurally different from SHA-2.

Ethereum and Keccak-256: Ethereum adopted Keccak before NIST finalized SHA-3. The NIST version added domain-separation padding, so Keccak-256 ≠ SHA3-256. Ethereum continues using the original Keccak-256 for compatibility.

Why Multiple Cryptographic Techniques?

Each primitive solves a different problem in the security and usability puzzle:

Component Purpose Why Not Use One Algorithm?
BIP-39/32/44 Key management and derivation Hash functions don't provide key hierarchies or human-readable backups. Public-key crypto can't derive child keys securely.
secp256k1 Public/private key relationship, signatures Hash functions are one-way with no trapdoor – can't sign or prove ownership. Need algebraic structure for ECDSA.
Keccak-256 Address derivation, state hashing Public keys are too long for addresses (64 bytes → 20 bytes). Need collision resistance without algebraic structure.
EIP-55 Error detection Pure encoding has no error detection. Full checksums (like base58check) add bytes. EIP-55 reuses existing characters cleverly.

The pipeline combines these primitives to achieve:

  • Usability: 12-word backup instead of raw hex keys
  • Security: One-way transformations, hardened derivation, collision resistance
  • Compatibility: BIP standards ensure cross-wallet compatibility; EIP-55 is backwards-compatible
  • Efficiency: secp256k1 uses 256-bit keys vs 2048+ bit RSA; Keccak is fast and parallel-friendly
  • Error prevention: Checksums catch typos before funds are lost

No single algorithm provides all these properties. Hashing alone can't sign transactions. Public-key crypto alone can't compress addresses or detect typos. The layered approach lets each primitive do what it does best.

Statistical Properties Summary

Randomness and Entropy

  • BIP-39 entropy: 128–256 bits of cryptographically secure randomness. Output (mnemonic) is deterministic but unpredictable without the entropy.
  • BIP-32 child keys: Appear statistically independent and uniformly random despite being deterministically derived.
  • secp256k1 public keys: Uniformly distributed across the curve. No correlation between sequential private keys and their public keys.

One-Way Properties

  • secp256k1: Discrete logarithm problem ensures Q = k·G is easy forward, infeasible backward (best attack ~2¹²⁸ operations).
  • Keccak-256: Preimage resistance (can't find input from hash), collision resistance (can't find two inputs with same hash).
  • BIP-32 hardened derivation: Parent public key cannot derive child private keys.

Avalanche Effect

  • Keccak-256: Changing 1 bit of input flips ~50% of output bits. Essential for checksum (EIP-55) and address collision avoidance.
  • PBKDF2 in BIP-39: Small passphrase change produces completely different seed.

Error Detection

  • BIP-39 checksum: Last word encodes checksum of entropy (4-8 bits). Detects most transcription errors.
  • EIP-55: Capitalization checksum. Probability of random typo passing checksum: ~2⁻¹⁵ per character.
